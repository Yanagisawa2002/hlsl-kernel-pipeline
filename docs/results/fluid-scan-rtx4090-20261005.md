# Unity fluid exclusive-scan application benchmark — RTX 4090, 2026-10-05

**Measured negative result for an acceleration showcase.** At 410,758 water particles,
the complete local exclusive-scan adaptation took 14% more time than the author's
Blelloch scan. None of the three arms established a clear whole-frame improvement.
The implemented integration and independent visual exports are working; this scene
does not currently support a claim that the local scan makes the application faster.

## Accepted results

All values are milliseconds per simulation frame: the median of three independent
process p50 values. Each frame contains three scan/sort/spatial calls. GPU boundaries
are nested and must not be added together. Scan includes pack/reset/unpack and padding
where required, rather than timing the inner kernel alone.

| Arm | Complete scan GPU | Complete count sort GPU | Spatial hash GPU | Complete simulation GPU | Whole frame wall |
| --- | ---: | ---: | ---: | ---: | ---: |
| Original Blelloch | 0.051200 | 0.128000 | 0.141312 | 5.102080 | 6.911900 |
| Local wave-tiled | 0.058368 | 0.136192 | 0.149504 | 5.126656 | 6.957900 |
| External GPUPrefixSums RTS | 0.037888 | 0.115712 | 0.128000 | 5.128192 | 6.989300 |

Local complete scan: +14.0% time. External complete scan: -26.0% time. Original scan
is only approximately 0.74% of original whole-frame p50, so the scan improvement in
the external arm is too small to establish an application benefit in this cohort.
This ratio compares descriptive medians; it is not an additive CPU/GPU breakdown.
Whole-frame per-process p50 ranges overlap: original 6.9064–6.96925 ms, local
6.9019–6.9901 ms, RTS 6.9096–6.9920 ms. No statistical significance, maximum-particle
capacity, or 60 FPS capacity improvement is claimed. The earlier large inclusive
scan experiment does not predict this exclusive application workload.

## Hardware and common configuration

- NVIDIA GeForce RTX 4090, 24 GB; Intel Core Ultra 7 265K; 32 GB RAM; Windows 11 build 26200.
- NVIDIA driver 617.14 (Windows driver 32.0.16.1714), Unity 6000.3.13f1, Direct3D12.
- Windows x64 Development Player; Graphics Jobs disabled for every arm; VSync off, uncapped rendering.
- Author's Fluid ScreenSpace 2 scene, screen-space water rendering and foam enabled; fixed camera, 1920×1080.
- 410,758 water particles; foam capacity 1,024,000 (capacity, not measured active count).
- Spawn density 600, seed 42, dt 0.01666666753590107 s, three solver substeps/frame.
- Each fresh process: startup full-output GPU validation, 120 warmup frames, 600 measured source frames (121–720).
- Balanced sequential order: original/local/RTS, local/RTS/original, RTS/original/local.

Recording was off during performance runs. Only normal visible Player runs with a
live backbuffer are accepted. Earlier hidden-window pilots could skip the complete
display chain and are excluded. No two simulation arms ran concurrently. Data are
instrumented Development Player measurements, not a release-player performance claim.

## Measurement and correctness

Unity Recorder produced no valid GPU samples on this built-in render pipeline.
The explicit native path inserts 20 D3D12 timestamps/frame on Unity's active
graphics command list. It associates each readback with an explicit source frame
and completed Unity frame fence; graphics-queue frequency was 1,000,000,000 Hz.
It does not flush, submit its own queue, or wait for a timing readback. All four GPU
metrics and the wall metric have 600 valid observations in every accepted process.
`gpuDelayValidated=true` is the legacy field for this completed frame association;
`gpuTimingMethod=d3d12_query_frame_fence` identifies the actual method.

Wall timing spans consecutive LateUpdates and includes rendering, presentation,
collector and instrumentation overhead. GPU simulation timing excludes rendering.
The original/local/external boundaries and instrumentation are the same. Native
plugin events may themselves have CPU/command-stream overhead; no overhead-free
timing is claimed. Error/assert/exception logs fail startup or measurement.

Each arm passed 80 full-output scan cases, 18 full-sort/permutation cases and
18 complete spatial-offset cases. Every performance and capture process repeats
that gate before simulation. Static checks passed 33 C# sources, 30 compute entry
points and 18 pure CPU settings cases. Native compilation passed `/W4 /WX`.

The Unity wrapper retains the actual shared wave32 algorithm and rejects an
observed native wave size other than 32; it has no alternate scan fallback.
The ordinary SM6.6 consumer is unchanged. All five vendored RTS inputs still match
their upstream source lock; only the generated Unity root declares the header's
VULKAN keyword. Both adaptations pass the same full-output GPU gate.

## Visual exports

After all measurements, each arm exported 600 initial-state frames separately with
the same seed/camera/quality and fixed timestep, while performance recording and
native timing were disabled. The three 1080p clips were then composed offline into
original/local and original/RTS split screens. Both include the measured values and
the negative whole-frame conclusion. Five delivered MP4s decode to 600 frames each,
1920×1080, 60 fps, 10 seconds. **60 fps is playback cadence, not measured FPS.**

The shared atomic scatter does not guarantee stable equal-key particle order;
independent arms need not remain pixel-identical. The comparison-preview frame was
visually inspected for water collision, foam, labels and composition. This does not
substitute for the full-output numerical correctness gate. Video hashes are in the
evidence bundle; the large local media files are not committed to the repository.

## Decision

**NO-GO for presenting this scene as an acceleration result for the current local
scan.** Keep it as a working application integration and honest negative benchmark.
Further optimization would require a separate measured investigation of the
complete adaptation and the actual dominant solver/render work. No capacity sweep
or additional optimization was run as part of this session.
